## 二、核心案例：代码段渲染问题 —— 一个修了 16 次才解决的问题

### 2.1 时间线

这是整个项目中最典型的"反复修不好"的案例。从第一次尝试到最终解决，横跨 **16 个 commit**：

| 轮次 | 做了什么 | 结果 |
|---|---|---|
| 1 | 修改 Markdown 转换正则支持多行 | 无效 |
| 2 | PIPELINE_VERSION 3→4 刷新缓存 | 无效 |
| 3 | **在 Readability 前用 `<p data-preblock>` 占位符"保护" `<pre>` 块** | 代码段直接消失 |
| 4 | 修复占位符正则的 Rust 转义语法错误 | 编译通过但代码段仍消失 |
| 5 | PIPELINE_VERSION 4→5 + 修复双重 `<code>` 嵌套 | 代码段仍消失 |
| 6 | **完全移除占位符保护，让 Readability 原生处理** ✅ | 终于正确 |
| 7 | PIPELINE_VERSION 5→6 强制旧缓存失效 | 用户端生效 |
| 8-16 | 处理边界情况：bare `<pre>`、syntax-highlight `<span>` 空格丢失、前端版本号漂移等 | 逐步完善 |

**耗费 16 个 commit 才彻底稳定。**

### 2.2 为什么修了这么多次？

**根因：AI 做了不该做的假设。**

AI 的思考链路：

```
"代码块格式丢失" 
  → 假设 Readability 破坏了格式
  → 在 Readability 前"保护" pre 块
  → 用 <p data-preblock> 占位符替换
  → Readability 把占位符 <p> 当空段落删了
  → 恢复正则找不到占位符
  → 代码段完全消失
```

正确的做法只需要一行代码改动：

```rust
// 之前（加了一堆保护代码）
pub fn extract(raw_html: &str, url: &str) -> String {
    let re_pre = regex::Regex::new(...).unwrap();  // 保护正则
    let mut placeholders: Vec<String> = Vec::new(); // 存储
    let protected = re_pre.replace_all(...);        // 替换
    let extracted = readability::extractor::extract(...);
    let re_ph = regex::Regex::new(...).unwrap();    // 恢复正则
    re_ph.replace_all(...)                           // 恢复
}

// 之后（删掉所有保护，直接传）
pub fn extract(raw_html: &str, url: &str) -> String {
    let extracted = readability::extractor::extract(...);
    extracted
}
```

**教训：在给第三方库加 workaround 之前，先用一个 5 分钟的单元测试验证原生行为。** Readability 对 `<pre>` 块的处理本来就是正确的——保留换行、保留缩进、保留 `<code>` 嵌套。

### 2.2.1 一个更深层的问题：AI 为何迟迟找不到根因？

回顾整个修复过程，AI 在每一轮都做了相同的事情：

1. 用户报告"代码段没了"
2. AI 读代码、改正则、修编译错误、跑 `cargo test`
3. 测试通过 → AI 认为"修好了"
4. 用户说"还是不行"
5. 重复步骤 2

**问题出在步骤 3：AI 只看编译结果和单元测试结果，没有去验证"用户实际看到的现象"。**

具体来说：
- 单元测试用的是简化的 HTML fixture（`<pre><code>fn main() {}</code></pre>`），Readability 能正确处理
- 但 AI 没去思考：用户的真实文章中，`<pre>` 块周围有大量中文文本、嵌套 `<span>`、语法高亮标记……这些才是 Readability 可能处理不好的场景
- 更关键的是，AI 始终没有去做一个最简单的验证——**把用户报告的那个具体文章拿出来，走一遍管线，看输出是什么**

这揭示了一个 AI 辅助开发的固有限制：

> **AI 能通过编译和单元测试，但无法替代"用真实数据跑一遍"的端到端验证。编译通过 ≠ 问题解决。**

开发者需要主动推动 AI 做更深入的排查：不是"代码段没了改正则"，而是"先用那个出问题的文章写一个端到端测试，看每一步的输出"。只有看到 Readability 原生输出里 `<pre>` 块被完整保留，才能意识到问题不在 Readability，而在我们加的"保护"代码。

### 2.3 为什么缓存让问题更难排查？

三层缓存机制来自 AGENTS.md 的设计：

```
Tier 1: cleaned_html 存在 && readability_version >= PIPELINE_VERSION → 直接返回
Tier 2: raw_html 在 DB → 用缓存的原始 HTML 重新跑管线
Tier 3: 抓取 URL
```

问题在于：每次代码修复后，DB 里已有旧版本缓存。如果忘记升 `PIPELINE_VERSION`，旧缓存永远不会重新处理。这导致：

- 开发者在本地测试"修好了"
- 用户拉代码后还是看到旧缓存的结果
- 来回沟通"你清一下数据库"——本质上是缓存失效没做好

**PIPELINE_VERSION 被升了 4 次（3→4→5→6），说明每次都没意识到需要再升。**

## 三、其他典型案例

### 3.1 Feed 添加卡死 UI（异步问题）

**现象**：添加订阅源时整个界面冻结。

**AI 的错误修复**：最开始用 `tokio::runtime::Runtime::new()` 在同步函数里嵌套异步调用。

**真正的修复**：全链路改 `async fn`，从 Command → Service → Repository 全部 `.await`。

**教训**：Rust 的 async 是传染的——如果在调用链中间使用 `block_on`，等于在所有异步之上盖了一个同步盖子。AI 倾向于"最小改动"，但异步问题往往需要"全链路改动"。

### 3.2 翻译跨文章串扰（状态绑定问题）

**现象**：切换到另一篇文章，翻译面板显示的还是上一篇文章的翻译。

**AI 的第一次修复**：加了 `TranslationState.mode` 字段。

**真正的修复**：`TranslationState` 必须同时绑定 `entryId`，`ReaderView` 用 `key={selectedEntry.id}` 强制重建。

**教训**：React 组件在 props 变化时默认复用 DOM。AI 容易忽略 React 的 reconciliation 机制，以为改了 state 就够了。

### 3.3 Toast 颜色被覆盖（CSS 优先级问题）

**现象**：错误 Toast 是绿色的，成功 Toast 是红色的——颜色反了。

**AI 的错误判断**：改了 Tailwind 类名。

**真正的修复**：Tailwind 类名被新的 UI 设计系统覆盖了，必须用内联 `style={{ backgroundColor: "#dc2626" }}` 才能确保优先级最高。

**教训**：AI 对 CSS 优先级和 Tailwind 的 `@layer` 机制理解不够，倾向于"换个类名试试"而不是分析为什么类名不生效。

## 四、AGENTS.md 约束文档的实际作用

### 4.1 哪些约束真正起了作用？

| 约束 | 效果 | 评价 |
|---|---|---|
| "所有业务逻辑在 Rust Core" | 架构始终保持三层分离，没有出现 React 直接操作数据库的情况 | ✅ 非常有效 |
| "阶段隔离，禁止修改上一阶段文件" | 新功能新建文件而非改旧文件，降低了回归风险 | ✅ 有效 |
| "PIPELINE_VERSION 缓存失效机制" | 提供了正确的缓存失效框架，虽然实际使用中多次忘记升版号 | ⚠️ 机制正确但执行不到位 |
| "Reader 管线固定 7 步流程" | 管线结构清晰，每一步职责明确 | ✅ 有效 |
| "数据库迁移只增不改" | 没有出现改表结构导致数据丢失的问题 | ✅ 有效 |
| "Agent 统一状态机 5 状态" | AI 摘要和翻译的行为可预测，没有出现状态混乱 | ✅ 有效 |
| "禁止 println!，用 tracing" | 日志体系统一，排查问题时有结构化日志 | ✅ 有效 |

### 4.2 哪些约束缺失导致问题反复出现？

| 缺失的约束 | 导致的问题 | 建议补充 |
|---|---|---|
| **"给第三方库加 workaround 前必须先写测试验证原生行为"** | 代码段问题修了 16 次 | 加到 AGENTS.md 技术约束 |
| **"修改管线后必须同时升 PIPELINE_VERSION"** | 用户拉代码后仍看到旧缓存 | 加到 Definition of Done |
| **"前端版本号禁止硬编码，必须从后端获取"** | 前端 PIPELINE_VERSION 漂移导致缓存不同步 | 加到 React 前端约束 |
| **"同一个 bug 修复超过 3 次未解决，必须停下重新评估根因"** | 占位符方案反复尝试 | 加到 AI 使用指南的"何时停下询问" |
| **"CSS 样式问题优先检查优先级和 @layer，而非改类名"** | Toast 颜色修了多次 | 加到 React 前端约束 |

### 4.3 约束文档的根本局限：无法真正限制 AI 的发散

这是实践中最深刻的感受之一。AGENTS.md 写了 400 多行，覆盖了架构、管线、测试、命名等方方面面，但在代码段问题中——

**AI 完全绕过了所有约束。**

复盘一下 AI 当时的"思路"：

```
AGENTS.md 说："所有业务逻辑在 Rust Core"
  → AI：没问题，我在 Rust Core 的 pipeline.rs 里改

AGENTS.md 说："Reader 管线固定 7 步流程"  
  → AI：没问题，我在 extract() 这一步里加预处理

AGENTS.md 说："数据库迁移只增不改"
  → AI：没问题，我没改数据库
```

**文档约束框住了"在哪里改"，但框不住"改的思路对不对"。** AI 的所有改动都在约束范围内——在 Rust Core 改、在管线内改、没碰数据库——但改的方向完全错了。

这说明约束文档的效力有一个清晰的天花板：

| 能约束的 | 不能约束的 |
|---|---|
| 代码放在哪个目录 | AI 对问题根因的判断 |
| 用什么库、什么框架 | AI 假设第三方库有 bug 然后擅自加 workaround |
| 函数命名风格 | AI 在错误的方案上反复迭代 |
| 测试必须通过 | AI 测试通过了但问题没解决 |

**约束文档是"护栏"，不是"导航"。** 护栏能防止车冲出悬崖（架构崩溃），但不能告诉司机该往哪开（根因在哪里）。导航需要开发者自己来。

### 4.4 一条被"合法绕过"的规则

AGENTS.md 中有一条规则：

> "如果发现 Mercury 原版设计存在缺陷：创建 ADR，提交人工评审。禁止 AI 自行优化产品行为。"

这条规则在代码段问题中**没有被触发**。因为 AI 不认为自己在"优化产品行为"——AI 认为自己在"修复 Readability 库的缺陷"。但本质上，AI 在没有验证的情况下假设了一个第三方库有 bug，然后擅自加了 workaround。

**这说明需要在约束中明确区分"产品行为"和"技术行为"——对第三方库行为的假设同样需要验证。**

## 五、AI 辅助开发的模式总结

### 5.1 AI 的优势（这些场景 AI 做得很好）

1. **样板代码生成**：Repository CRUD、Tauri Command 注册、前端 API 封装——一次生成，基本正确。
2. **跨文件重构**：异步化改造（同步→async）涉及 5+ 文件，AI 能一次性找出所有需要改的地方。
3. **测试编写**：给出现有代码，AI 能生成覆盖边界情况的测试。
4. **错误信息解释**：Rust 编译错误对新手不友好，AI 能翻译成人类语言。

### 5.2 AI 的劣势（这些场景 AI 容易出错）

1. **假设第三方库行为而不验证**：Readability 案例中最典型——AI 假设库有 bug 然后加 workaround。
2. **缓存/状态一致性问题**：版本号、缓存失效、状态绑定——这些"跨时间"的问题 AI 容易遗漏。
3. **CSS 优先级和级联问题**：AI 倾向于"试试另一个类名"而非分析根本原因。
4. **最小改动倾向**：AI 倾向于在现有代码上打补丁而不是重构，导致技术债务积累。
5. **跨会话上下文丢失**：新 AI 窗口不知道之前试过什么方案，会重复尝试已失败的方案。
6. **满足于编译通过**：AI 把 `cargo test` 通过视为"问题解决"，不去验证用户实际看到的渲染结果。这也是为什么代码段问题反复了 16 次——每轮 AI 都觉得"编译过了，测试过了，应该好了"。
7. **文档约束的边界效应**：如 4.3 节所述，约束文档能框住"在哪里改"但框不住"改的方向对不对"。AI 可以在遵守所有规则的前提下走向完全错误的方向。

### 5.3 有效的人机协作模式

| 模式 | 说明 | 效果 |
|---|---|---|
| **先写测试再改代码** | 让 AI 先写一个验证原生行为的测试，而不是直接改代码 | 能避免 16 次反复 |
| **约束文档前置** | 把 AGENTS.md 作为 system prompt 的一部分，AI 每轮都先读 | 架构一致性保持良好 |
| **上下文文档接力** | SESSION_CONTEXT.md 让新 AI 窗口快速了解历史 | 刚建立，待验证 |
| **3 次修不好就停下** | 如果同一个 bug AI 修了 3 次还没解决，人工介入重新分析根因 | 应该加到约束中 |
| **提交粒度小** | 每个 commit 只做一件事，方便 `git revert` | 回滚方便 |
| **明确要求 AI "加深搜索"** | 当 AI 说"修好了"但问题依旧时，不要接受表面修复。要求 AI：①用真实数据跑端到端测试 ②打印每一步的中间输出 ③对比预期和实际。代码段问题最终解决正是因为用户反复说"还是不行"，迫使 AI 写了 `test_readability_raw_pre_behavior` 测试才发现了真相 | **最关键的一条** |

### 5.4 "加深搜索"的具体操作指南

基于本次项目经验，当 AI 反复修不好同一个问题时，开发者可以用以下话术推动 AI 深入排查：

| 不要说 | 要说 | 原因 |
|---|---|---|
| "代码段还是没了" | "用那个具体文章写一个测试，把 extract/sanitize/markdown/render 每一步的输出都打印出来" | 让 AI 看到中间状态 |
| "修一下这个 bug" | "先不要改代码，先写一个能复现这个 bug 的测试，确认测试确实失败" | 防止 AI 在错误方向改代码 |
| "检查一下哪里有问题" | "对比一下 Readability 的输入和输出，看 <pre> 块在哪一步丢失的" | 缩小排查范围 |
| "改好了吗" | "不要只看 cargo test 的结果，告诉我用户实际会看到什么" | 推动端到端验证 |

## 六、给后续开发的建议

1. **在 AGENTS.md 中增加"第三方库验证规则"**：任何对第三方库行为的假设必须先通过单元测试验证。
2. **在 DoD 中增加"版本号检查"**：如果修改了 reader 管线，必须同时升 PIPELINE_VERSION。
3. **创建 `.cursor/rules` 或 `.github/copilot-instructions.md`**：把关键约束以 AI 能直接读取的格式放在项目根目录。
4. **每次会话开始时让 AI 先读 SESSION_CONTEXT.md**：3 分钟内了解项目现状和近期踩过的坑。
5. **建立"3 次修复法则"**：同一个 bug 如果第三次 commit 还没解决，创建 issue 让人工评审。

## 七、实践者的真实感受

> 以下来自项目开发者的第一手体验总结。

### 7.1 文档约束有用，但有天花板

AGENTS.md 确实帮了大忙——三层架构从未被破坏，管线流程始终清晰，数据库迁移没有出过事故。这些"硬约束"（目录结构、命名规范、禁止事项）AI 执行得很好。

但文档做不到的是：

- **无法预见 AI 的发散方向。** 写文档时想不到 AI 会给 Readability 加"保护"——这是 AI 自己"想"出来的方案。文档只能禁止已知的错误，无法预判 AI 会创造什么新的错误。
- **AI 可以在遵守所有规则的前提下走错方向。** 代码段问题的每一轮修复都在 AGENTS.md 的规则范围内，但方向完全错了。
- **约束越多，AI 越擅长"合法绕过"。** 就像 4.4 节分析的——AI 总能找到一个不违反规则的解释来合理化自己的行为。

### 7.2 AI 满足于"编译通过"，但问题在编译之外

这是最让人沮丧的模式：

```
开发者：代码段没了
AI：    我改了正则，cargo test 全过了 ✓
开发者：还是没了
AI：    我修了转义问题，cargo clippy 零 warning ✓  
开发者：还是没了
AI：    我升了版本号强制刷新缓存 ✓
开发者：还是没了
...（重复 16 次）
```

**AI 的"完成标准"和开发者的"完成标准"不一样。** AI 的标准是编译通过 + 测试通过。开发者的标准是"用户打开文章看到正确的代码块"。这中间的差距，就是 AI 反复修不好的根源。

推动 AI 跨越这个差距，需要开发者明确说："不要只看测试结果，用真实数据跑一遍给我看输出。"

### 7.3 "加深搜索"是开发者必须主动要求的

默认情况下，AI 的排查深度是"读代码 → 改代码 → 跑测试"，大约 2-3 层。但代码段问题需要大约 5-6 层：

```
第 1 层：代码段没了 → 可能是正则问题
第 2 层：改正则 → 编译报错 → 修语法
第 3 层：编译过了 → 测试过了 → 用户说还是不行
第 4 层：加占位符保护 → 代码段彻底消失
第 5 层：修占位符正则 → 测试过了 → 还是不行
第 6 层：写原生行为测试 → 发现 Readability 根本不需要保护 ← 真相在这里
```

AI 自己不会主动挖到第 6 层。它会在第 2-3 层循环，每次都告诉你"修好了"。**需要开发者一次次说"不对，再往深挖"，AI 才会进入下一层。**

这不是 AI 的能力问题——AI 完全有能力写到第 6 层。这是 AI 的**默认行为**问题——它默认在浅层就停下来。改变这个默认行为，需要开发者主动推动。
